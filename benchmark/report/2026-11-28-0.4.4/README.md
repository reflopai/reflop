## 2. Findings

Written by hand after the run, from these tables and from follow-up measurements on the Owner (§2.3, §2.4), which are not in `data/`. Section numbers below refer to this document.

### 2.1 Verdict in one paragraph

reflop 0.4.4 passes all 697 cases that ran (683 pass, 14 xfail, 0 fail). The 20 skips are a15, which needs the Owner's hardware on the Guest's side. 0.4.1 had 6 failures. 3 of those cases now pass, and the other 3 were rewritten for the behaviour 0.4.0 changed on purpose, under new names that pass. a13 ran all 16 cases for the first time, so invites, isolation between identities and all six quotas are now tested end to end. Speed is unchanged except where 0.4.4 changed it. ResNet-18 captured at batch 128 fell from 5.815 to 4.563 ms per step (−21.5 %), the max pool sync removal (ADR-065). Two questions the 0.4.1 report left open are answered. Opening a session takes 3.4 s, and 98 % of that is the Owner starting the worker. The 18 ms of extra LSTM and GRU time per step comes from the Owner's default `rnn_fused = false`, not from the network, the client or Python (§2.4).

### 2.2 Confounders

1. **The network was the same.** Tailscale reported a direct path both times. The b03 GPU RTT median was 4.571 ms, against 4.109 ms in OLD (+11 %). The link carried about 10.5 MiB/s in both runs (64 MiB upload 10.52 MiB/s, both runs).
2. **The GPU ran faster in NEW.** Native CUDA took a median 4.7 % less time per step (§7.4). A flat reflop time therefore means slightly more overhead. Compare overheads, not raw times.
3. **Three releases apart.** 0.4.2 added `reflop test` and the Owner commands by name, and 0.4.3 changed only the client's `reflop test` output. Neither changed the execution path. The only change on the execution path is 0.4.4's.

### 2.4 Why LSTM and GRU are 20–30× slower than native

LSTM keeps 5.0 % of native speed, and GRU 3.3 %. A captured LSTM step at batch 128 took 34.4 ms over the network. The same step run in-process on the Owner (`reflop.device(local="cuda")`, no daemon) takes 13–18 ms. The cause was measured on the Owner with a throwaway reflopd and a local Guest. That removes the network and the Mac:

| b128, b01's model and step | ms per step |
|---|---|
| in-process (no daemon) | 13–18 |
| reflopd, defaults, Guest on the same machine | 39.5 |
| reflopd with `[ops.capabilities] rnn_fused = true` | 17.9 |
| GRU, defaults → `rnn_fused = true` | 40.0 → 19.2 |
| LSTM eager, defaults → `rnn_fused = true` | 378 → 158 |
| GRU eager, defaults → `rnn_fused = true` | 383 → 154 |

- reflopd turns `rnn_fused` off by default (PLAN.md O11). It then leaves `_thnn_fused_lstm_cell`, `_thnn_fused_gru_cell` and their backwards (ops 560–563) out of the session's operators. The client then records each LSTM or GRU cell as its elementwise parts. A worker profile shows 8,182 ATen calls per captured LSTM step through reflopd, against 2,550 in-process. In-process sessions enable every operator the device has, which is why they never showed the gap.
- The sandbox does not slow the worker down. Inside the worker, before and after seccomp, `aten.add` on a 128×128 CUDA tensor takes 2.86–2.88 µs per call, the same as outside (2.86–2.91 µs). With the worker's environment variables, the in-process step still takes 18 ms, and the worker's bundled Python makes ATen calls as fast as the Guest's. In a profiled window of 40 requests the worker waited for requests for 11 ms out of 1,749 ms, so the client and the network are not what limits it.
- O11 kept `rnn_fused` off because of `_cudnn_rnn`'s validation complexity. ADR-051 has since banned `_cudnn_rnn`, and `rnn_fused` now covers only the four `_thnn_fused_*` cells, which have prechecks (`prechecks.py`) and CUDA meta-parity seeds (`test_meta_parity.py`). Whether to turn them on by default is a separate decision.
- reflopd advertises `rnn_fused` among its capabilities even while the Owner's config turns it off, because the capability list is built from the worker's report without the config's toggles (`capabilitiesFor` in `server/reflopd/internal/server/server.go`). The client decides from the operator list, so only `reflop status` is misleading.

### 2.5 Sessions and the link (§7.6)

- **Opening a session (a06):** 3,469 ms on cuda, of which 19.6 ms is the authenticated handshake, 3,403 ms the worker start and 7.8 ms the first op. On cpu: 19.6 + 3,182 + 7.7 ms. The worker start matches reflopd's self-test on the Owner (worker ready in 3.354 s cuda, 3.119 s cpu). The 0.4.1 report's 3.4 s is therefore the Owner starting a sandboxed Python worker that imports PyTorch and initializes CUDA. The network is not part of it.
- **The link is the limit for transfers (b03 `link`):** plain ssh to the Owner moved 10.54–10.58 MiB/s up and 8.82–9.93 MiB/s down. reFLOP moved 10.34–10.48 MiB/s up and 10.04–10.22 MiB/s down over the same path (ratio 0.98–1.16). Upload-policy steps are bound by this link, not by reFLOP's protocol. A faster link, or data on the server (a dataset: cnn 2.282 ms per captured step, a07), is the way to speed them up.

### 2.6 Other measured changes (§7.6)

- **Concurrency (a14, captured CNN, batch 128):** aggregate samples/s for 1/2/4/8 processes 48,399 / 74,111 / 89,384 / 93,881, against 45,797 / 69,801 / 81,627 / 80,939. 8 processes reach 1.94× one process (OLD 1.767×), with Jain fairness ≥ 0.9998. The CNN has a max pool, and 0.4.4 removed a device sync from each of its steps. That fits the larger gain at 8 processes, where a sync also waits for the other processes' kernels, but this run does not prove it.
- **Soak (b04, captured GPT from a server dataset, 20 min):** 80,750 steps against 83,300 (−3.1 %), median 14.62 ms per step (OLD 14.20). It was steady over the whole run, with RSS flat at 319 MiB and a loss of 4.571 → 2.836. NEW was slower in nearly every half-minute sample, so the difference is real, but its cause is unknown: b01's captured GPT got 5 % faster in the same run.
- **Checkpoints (a12):** all 8 cases pass, including CPU worker crash → recover (new). Step time with checkpoints on: median 26.78–27.69 ms (OLD 26.79–26.80). Recovery took 3.655 s (GPU) and 3.394 s (CPU). The first checkpoint lands after 59.7–59.9 s.
- **Owner pause --now (a11):** GPU session suspend and resume: pause 0.6574 s, resume 0.5014 s, Guest stall 9.178 s. A CPU session is now frozen and thawed (pause 0.1154 s, Guest stall 6.225 s), the 0.4.0 behaviour the 0.4.1 suite still tested the old way.
- **Quotas (a13):** the upload-bandwidth quota at 1 MiB/s held 12.03 MiB to 0.9153 MiB/s (13.15 s, against 1.659 s unlimited). Device memory, sessions, wall time, FLOPs and storage quotas refuse with the documented errors.
- Matmul, snapshots, datasets, the C API, recording cost and the graph cache changed by amounts within their latency and link spread (§7.5–7.6).
