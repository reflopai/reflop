### 2.1 Verdict in one paragraph

reflop 0.4.1 (client and daemon) passes 662 of 682 cases (6 fail, 14 xfail, 0 skip) against 657 / 17 / 22 for 0.2.2. 24 cases improved status (16 fail→pass, 8 xfail→pass). Of the 6 failures, 1 is a reflop bug still open since 0.2.2, 3 are tests written for 0.2.2 behaviour that 0.4.0 changed on purpose, and 2 are a harness incompatibility that also stopped 14 a13 cases from running (§2.6). Raw GPU step times fell by a median of 11.7 % over all 130 b01 configurations. But the network round trip between Guest and Owner also fell from 15.59 ms to 4.109 ms between the two runs (§2.3). With that removed, reflop's own measurable speedup is concentrated in graph-heavy workloads: LSTM and GRU captured steps take 17.7–20.8 % less time at batch 128, the gain the 0.4.1 changelog describes for those models. GPT shows no gain (§2.4).

### 2.2 Confounders that must be considered before reading any speedup

1. **Network latency differs between runs (largest confounder).** b03 RTT median of a tiny op + `.item()`: GPU 15.59 → 4.109 ms (−73.6 %), server CPU 15.5 → 4.129 ms. `reflop init` measured rtt_ms 15.18 (OLD) and 3.97 (NEW). The reflop changelogs 0.2.3–0.4.1 contain no latency change. On 2026-11-28 Tailscale reports a direct LAN path (`pong from <server> via <ip>:41641 in 3ms`; ICMP ping avg 5.937 ms, min 3.221 ms). The OLD run's network path was not recorded, so its 15 ms is most likely a different path (another network or a relayed connection), not reflop. Every latency-sensitive number (RTT, C API execute+fetch, small-batch steps, session close) is therefore not a fair reflop-vs-reflop comparison.
2. **The GPU itself ran slower in NEW.** Native CUDA (unchanged code, same torch 2.15.0+cu132) took a median 6.0 % longer per step in NEW (range −13.2 % to +34.8 %, 60 configurations, §7.4). Native matmul peak fell ≈5–6 % (bf16 8192: 68.54 → 64.59 TFLOP/s). Raw reflop Δ% therefore *understates* reflop's improvement by about that much on GPU-bound workloads. Overhead (reflop − native, same run) removes this drift.
3. **Upload bandwidth was steadier in NEW.** The transfer sweep gives ≈10 MiB/s both runs (1 MiB upload 8.397 → 9.398 MiB/s; 16 MiB 9.834 → 10.4 MiB/s). But the bandwidth implied by b01 upload-minus-resident step times ranged 5.1–14.9 MiB/s in OLD and 10.6–16.1 MiB/s in NEW. The very large upload-policy gains (e.g. resnet18 b32 capture upload 180.3 → 37.07 ms, −79.4 %, with identical 393,472 bytes/step) come from link variance. OLD ms_reps for that row were [180.3, 208.6, 81.3]; NEW [36.99, 37.07, 37.07].
4. **Noisy OLD repeats.** Some large eager-resident gains come from OLD outlier repeats: cnn b32 eager resident OLD ms_reps [60.94, 22.86, 8.87] vs NEW [4.5, 3.65, 3.59] (reported −84.0 %); cnn b128 eager resident OLD [10.43, 7.49, 10.66] vs NEW [5.09, 3.82, 3.70]. Treat single-row changes above ±30 % in eager mode as noise unless the ms_reps agree.
5. **The OLD→NEW span covers 14 releases (0.2.3 … 0.4.1), not just 0.4.1.** The 0.4.1 changelog's figures (captured steps at batch 128 on an RTX 5070 take 21–25 % less time for MLP, LSTM, GRU, transformer, GPT, LoRA and autoencoder, and 6–11 % less for CNN, U-Net and ResNet-18) compare 0.4.0 → 0.4.1 on a local connection. They are not directly comparable to these numbers.

### 2.6 Correctness

- **Numerical results:** final training loss of all 130 b01 configurations is bit-identical between 0.2.2 and 0.4.1 for mlp, attn, gru, lstm, lora and all server-CPU rows. Differences appear only on cuDNN-convolution/BatchNorm workloads: resnet18 12/12 rows (max relative 2.77e-2), cnn 8/12 (3.68e-3), unet 12/12 (8.04e-5), autoenc 6/12 (7.16e-7), gpt 2/12 (1.01e-7). Native CUDA alone varies run-to-run on the same workloads (resnet18 up to 9.11e-3, cnn up to 1.99e-3, unet up to 3.67e-5; mlp and gpt 0). So these are GPU nondeterminism, not a regression. resnet18's reflop spread (2.77e-2) is ≈3× the native spread and could be checked with deterministic algorithms.
- **Fixed since 0.2.2 (fail → pass, 16 cases):** randint/randperm (KeyError: 4) on GPU and CPU; ctc_loss with tensor lengths (Meta kernel missing) on GPU and CPU; BatchNorm running stats when the output is discarded (baseline bug B3) on GPU and CPU; clip + hooks + accumulation across GPU/CPU sessions (CPU); capture re-capture after a shape/dtype change (baseline bug B2, was BINDING error); seed reproducibility with two sessions; 8 threads sharing a session; `autocast("cuda")` under `reflop run` (baseline bug B7, was a silent fp32 no-op); 64 MiB transfer (baseline bug B9); dataset build from iterables/dtypes and dict push (two harness bugs fixed after the OLD run, not reflop changes).
- **Newly supported (xfail → pass, 8 cases):** cholesky, linalg_inv_det, linalg_solve (`aten._linalg_check_errors` now available) and cross/tril/triu (`aten.to.dtype` decomposition, 0.3.2 GH#56), each on GPU and server CPU.
- **Still unsupported (14 xfail, identical to OLD):** argsort (`aten.sort.stable` not in opset v1), embedding_bag (`aten._embedding_bag_forward_only`), histc/bincount (`aten.histc`), and explicit `torch.Generator`, each on GPU and CPU; `torch.compile` (GPU and CPU); `reflop.capture` with non-capturable Adam / AdamW / Adamax (explicit CaptureError, 12/12/6 Python scalars changed between steps); AMP + GradScaler under capture (explicit CaptureError: reads a value on the host mid-step).
